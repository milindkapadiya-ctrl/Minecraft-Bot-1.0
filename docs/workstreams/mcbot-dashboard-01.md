## Product and integration

Dependency-free local HTML/CSS/JavaScript provides three task buttons, cancellation, safe reset, measured inventory, an ordered activity timeline and twenty recent results. SIMULATION remains prominent; real Minecraft is visibly disabled. All resources are local; no CDN, cloud, spending or new package is involved. Responsive CSS and frontend behavior are checked non-graphically; no rendered-browser inspection is claimed.

The backend imports the existing EvaluationBot/ResourceCourseBot fixtures explicitly as an offline composition. The default resources at1/2/3 on the existing east-facing course are the unchanged `original-three` evaluation fixture. ActionRunner performs real inspection, CollectionSequence/CollectionEpisode perform authenticated selection and whole-operation ownership, and the existing scanner, movement, digging, simulated server confirmation and independent retained-inventory verification run unchanged. The first collection is adjacent; later episodes contain actual guarded movement/scanning. No predetermined result or fixture truth enters the planner.

Only action-start/result events from the canonical runner feed progress. Completion of target selection or planning is not invented while unavailable; final episode evidence records actual selections, scans and arrivals. Inventory comes from a controller-owned measurement, with retained evidence displayed separately from each episode. Static decorative blocks do not pretend to be a live game view.

## Local security and lifecycle

The server binds only127.0.0.1; an alternate host configuration refuses. An OS-selected port is printed at launch. Exact Host checks protect against DNS rebinding; Origin and Fetch Metadata checks reject cross-site access. Mutations additionally require an exact same-origin Origin, JSON content type and a random256-bit process-session token obtained through the same-origin bootstrap. No permissive CORS is emitted. This protects against browser cross-site requests, not malicious programs already running as the local user.

Routes/static assets are explicit maps, never request-derived filesystem paths. The API accepts only inspect/one/three high-level task types, bounded opaque IDs and exact payload keys. JSON bodies are limited to1024bytes; connections to20, headers to30, and request/header timeout settings to5s. CSP disallows external resources, inline scripts, framing, forms and alternate base URLs; responses are no-store and nosniff. No raw Bot, controller scope, scanner snapshot, executable input or server-admin action is exposed.

One active task is reserved synchronously before asynchronous work. A process-lifetime set remembers up to1024 consumed IDs and then refuses further admission rather than forgetting replay protection. History is bounded to20 tasks and each timeline to100 events. Monotonic revisions prevent older polling responses from replacing newer UI state. Polling is sequential every750ms; frontend duplicate-click suppression is convenience only, with backend admission enforcing exclusion across tabs.

Each task uses existing component limits and an outer97s bound; the three-episode sequence stops at its first failure. Cancellation propagates through AbortSignal. The UI remains stopping until controls/controller release, pending fixture deliveries and a fresh exact settled-pose window have been checked. An uncertain cleanup closes admission, disposes fixture deliveries and blocks reset. Reset is allowed only from confirmed idle/settled state; it closes the old controller, disposes physics/timers/listeners and creates a new Bot and session ID. Consumed task IDs survive reset. Shutdown cancels active work, closes the HTTP listener/connections, closes the controller and disposes the fixture. No background simulation survives process shutdown.

## Future real-game boundary — design only

Replace the compiled simulation composition behind the task manager with a separately reviewed trusted pilot adapter. Preserve the interface of high-level task admission, read-only status/evidence, cancel and bounded close. Do not expose raw movement, digging, Bot handles or privileged world/server commands. A real reset must never recreate worlds or erase attempt consumption; it requires a different explicitly authorized session lifecycle.

The concrete HTTP boundary to retain is `start(id, kind) -> admitted TaskRecord`, `snapshot() -> copied status`, `cancel(id) -> request acknowledgment`, `reset() -> safe simulation reset`, and `close() -> Promise<void>`. A future compiled task-service adapter should implement these methods while delegating real collection to the existing trusted pilot session association, rather than constructing another ActionRunner. Server composition currently accepts Simulation directly; introducing a structural task-service interface and real adapter is a deliberate future review point, not an already implemented live integration. Real mode must reject collect-three and reset at backend admission, with explicit capability metadata reflected in the UI.

Activation review must verify: explicit one-attempt authorization; source-gate change reviewed separately; real trusted session registration and canonical controller; actual air/physics/connection readiness; permanent attempt identity/evidence; one-episode limit; cancellation and confirmed disconnect; honest cleanup uncertainty; no retries; loopback authorization; fresh integration/security tests. The current three-episode simulation button must not automatically become three real episodes. Technical resource-collection acceptance remains separate from advisor-video/human acceptance and the unconsumed DEMO-02 campaign.
