# Nearby block tools (Milestone 2)

Start **Start Test Server.cmd**, wait for `Done`, then start **Start Movement Demo.cmd**. Join Java 26.1 Multiplayer at `localhost:25565` to watch **SurvivalBot**. The bot terminal is the window opened by Start Movement Demo.cmd. It accepts the commands below and disconnects after ten minutes. `cancel` stops the current action; `quit` disconnects. Type `stop` in the server terminal when finished.

After source changes, run `pnpm check` in the project folder before launching (it builds the runnable files).

1. On clear, flat ground, use `look 0 -37` to face north and downward. Other yaw values turn the view; angles are degrees.
2. Enter `inspect`. Read `details.blocks` in the `action_result`. Entries are indexed from **0**, in the displayed order. Only first-hit surfaces in the current viewing cone, within four blocks, are returned. This is a sparse view, not a complete nearby-block scan.
3. Choose a visible surface block ahead. Enter `approach 2` to approach entry 2, for example. For same-height targets, this accepts only short, straight, flat routes with visible solid support and clear space. Noncolliding wildflowers are allowed; other plants, obstacles, gaps, slopes, unknown terrain, and liquids cause refusal. Results include the specific failed route check when applicable. A refusal is expected on many natural routes. That flat mode does not jump or route around obstacles; adjacent height changes use the step modes described below.
4. For a visible surface outside the bot's own support, enter `dig 2` using the same entry. The guarded dig currently supports dirt, grass blocks, sand and stone at the adjacent floor level. It also permits one cardinal-adjacent dirt/grass wall block at foot level, allowing a visible lower floor to be inspected before a guarded descent. Targets are rechecked, so stale or hidden targets fail. Underfoot, distant wall or other-level blocks remain unsupported. There is no automatic retry. Stone is refused unless a harvestable pickaxe is **held**.
5. Enter `inventory`. Dig results contain `inventoryBefore`, `inventoryAfter`, `serverConfirmedAir`, and (when both inventory snapshots were taken) `collectionEvidence`. The latter reports the expected drop count across slots before and after the action, its delta, and one of `inventory_increase_observed`, `not_observed`, or `unverified`. Expected drops are dirt from dirt/grass, sand from sand, and cobblestone from ordinary stone. `ok` still means only that the server confirmed air at the target. A positive relevant delta with a confirmed dig is evidence that the item entered inventory during the action, but does not prove which block supplied it if other pickups occurred. No increase does not prove a drop was absent; a failed or cancelled dig cannot establish collection. For descent, inspect the exposed lower floor and use guarded `step_down <index>` as described in `step-down.md`, rather than blindly issuing timed movement into the hole.

### Tool rules for Minecraft Java 26.1

The bot reads the block's `harvestTools` IDs from the installed 26.1 game registry and compares them with its **held** item before starting a dig. Mineflayer's `canDigBlock` checks reach and diggability but does not ensure a resource drop. A refusal returns `required_tool_not_held`, `heldTool`, `requiredTools`, and `availableInInventory`. A suitable tool in inventory still needs to be equipped; this action does not equip it automatically. Unbreakable or unknown-hardness blocks return `unbreakable_or_unknown`. All physical visibility, footing, range and time guards still apply.

| Example block           | Tool required to harvest its drop in 26.1                         | Guarded `dig` action           |
| ----------------------- | ----------------------------------------------------------------- | ------------------------------ |
| Dirt, grass block, sand | None; hand works (shovel only speeds digging)                     | Supported                      |
| Stone                   | Wooden, copper, stone, golden, iron, diamond or netherite pickaxe | Supported with held tool       |
| Iron ore                | Copper, stone, iron, diamond or netherite pickaxe                 | Material currently unsupported |
| Diamond ore             | Iron, diamond or netherite pickaxe                                | Material currently unsupported |
| Obsidian                | Diamond or netherite pickaxe                                      | Material currently unsupported |
| Bedrock                 | Cannot be mined                                                   | Refused                        |

The registry covers other block types too, but this small action's material allowlist prevents broad mining. `collect <index>` remains limited to adjacent dirt/grass pickup. The table concerns **harvesting a drop**: Minecraft may let a player break some blocks with a weaker tool but yield nothing. The bot refuses those wasteful attempts. This does not model Silk Touch, Fortune, special block states or every item drop.

For a **cardinal-adjacent** visible dirt/grass target on the same surface level, `collect <inspect index>` combines that dig with one guarded step into the hole if pickup was not already observed. It looks into the newly exposed hole and requires a freshly visible lower support block. Existing `step_down` checks the source, landing, buffer, clearance and motion; a refusal stops without extra movement. The command then observes dirt inventory for at most one second. `collect_result` reports `inventory_increase_observed`, `not_observed`, or a structured dig/landing/movement/cancellation failure. The full sequence is bounded to 12 seconds and never repeats the dig or movement. A distant, diagonal, hidden or unsafe hole cannot be entered by this command. No sand support, item-entity tracking or general navigation is implied.

To watch the bot's view on an authorized local test server, join with a different player name. The **server operator**, not the bot, can enter `gamemode spectator <player>` and then `spectate <bot> <player>` in the server console. Restore the observer with `gamemode survival <player>` before stopping the test. This changes only the observer's camera/game mode and never grants the Survival bot commands or items.

For an immediately adjacent support target one level higher/lower, `approach` now selects guarded step-up/down automatically. The step lands on the selected support (or its checked lower buffer); same-height approach still stops short of its target. It does not combine flat travel with a distant step, chain multiple height changes, or search routes. Use `details.strategy` to see the selected step and do not try to dig the block now underfoot.

Actions share one runner; overlapping requests fail with `busy`. Inputs have strict schemas, copied target coordinates/state IDs, and deadlines up to five seconds. Movement clears controls on all exits; dig cancellation also stops digging. Damage, death, disconnect, server position correction, or invalid physics interrupts an action. Ordinary coasting after releasing controls is expected.

For callers, the new action shapes are `{type:"inspect",timeoutMs:1000}`, `{type:"inventory",timeoutMs:1000}`, and `{type:"approach"|"dig"|"step_up"|"step_down",target:{x,y,z,stateId},timeoutMs:5000}`. Use targets from observations, never world files or privileged coordinates. All tools are deterministic; no model calls or resource strategy are included.
